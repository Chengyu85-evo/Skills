# PRD 撰写

按既有方法论产出 PRD。核心不是套模板，而是执行 `references/writing-rules.md` 里的生成规则——模板只保证不缺章节，规则才决定文档能不能让开发一次看懂。

## 工作流

### 1. 解析输入并判断任务类型

先确认用户提供的 PRD 来源，再进入对应流程：

- **飞书文档 URL / token**：切到 `lark-doc` 读取；评审先按需读取，修改按 `lark-doc` 的精准编辑链路执行
- **用户直接粘贴正文**：基于当前文本处理
- **本地 Markdown / Word 文件**：使用对应文档能力读取，保留原格式交付
- 用户要求评审或迭代、但尚未提供原文时，只追问文档 URL、文件或正文，不猜测文档内容

| 用户意图 | 动作 |
|---|---|
| 新写 PRD | 走第 2-5 步 |
| 给已有 PRD 补内容 / 改需求 | 跳到「迭代已有 PRD」 |
| 评审 PRD 完备性 | 跳到「评审模式」 |
| 评审并修改 | 先走「评审模式」给出问题，再走「迭代已有 PRD」局部修改 |

### 2. 收集输入，缺口一次问清

写之前必须拿到或确认：

- **需求本体**：要解决什么问题、目标用户场景
- **Meego 链接**（有则要）
- **Figma / 设计稿链接**（有则要）
- **目标版本号**（如 7.68）与是否走 FG
- **涉及端**：PC / Android / iOS / 会议室 / 服务端
- **需求类型**：数据驱动迭代 / 创新探索 / 体验修复 —— 决定第 3 节怎么写，必须明确

缺失项**一次性列出来问**，不要逐条追问。用户明确"先出框架、细节待补"时，用 `TBD` / `WIP` 占位并在文末汇总待确认项，不要静默留空。

### 3. 写正文

读 `references/prd-template.md` 拿章节骨架，读 `references/writing-rules.md` 拿生成规则。**两个都要读**，模板决定有什么章节，规则决定每节怎么写。

写作时逐节自检规则命中情况，尤其：功能点是否用「现状 / 预期」对照、条件是否成对、FG 是否双向、文案是否分视角、优先级规则是否有兜底。

### 4. 交付

默认建飞书文档：切到 `lark-doc` 创建。创建成功后，在最终回复中提供可点击的飞书文档 URL。

用户明确要本地文件时才落本地。

### 5. 交付前门禁

见 `references/writing-rules.md` 末尾的检查清单，逐条过。**第 3 节（需求目标与验收）留空或只剩标题时不允许交付**——三种填法任选其一，含"不设数据观察"的显式声明。

## 迭代已有 PRD

1. 先用 `lark-doc` 的 `docs +fetch --scope outline` 看结构，再按需局部精读，不要整篇拉取
2. 定位要改的章节，**局部更新**，不要整篇重写
3. 写 Change Log 前解析日期和操作人：日期取当前时区的实际日期；操作人只使用当前飞书身份返回的已验证姓名。无法验证时一次性询问或填"待确认"，禁止猜测
4. **同步在 Change Log 加一行**：日期 + 操作人 + 主要内容 + 详细变更。这是硬要求，改了正文不记 Change Log 等于没改
5. 被推翻的旧方案**用删除线保留在原地**，不要删除
6. 涉及新增文案或埋点时，同步更新「需求交付」里的"本次新增"清单

## 评审模式

除非用户明确要求“评审并修改”，否则不改文档。按 `references/writing-rules.md` 的检查清单逐条核对，输出问题清单。每条给出：**位置 + 问题 + 具体改法**。

优先看这几个高频失分点：

- 第 3 节空白或只有占位符（如"渗透率 X"未替换成实际数值）
- 竞品分析只有描述、没有"我们的取舍"
- 优先级规则没写兜底情况
- FG 只写了名字，没写命中/未命中双向表现
- 文案没分视角
- 迭代型需求缺「当前生效规则」快照，读者要读 N 篇文档才知道线上现状
- 标题层级跳跃（`#` 直接到 `###`）、编号重复
- 标题里塞进大段正文（如把多个 FG 说明写进二级标题）

## 边界

- 本 skill 仅面向**客户端版本制 + FG 灰度**的交付模式，不套用于 AB 实验驱动的服务端需求
- 产出中文文档，不做双语对照
- 不写技术方案（接口、数据结构、时序）；这些引用 TDD 链接即可
