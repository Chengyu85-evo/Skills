# 拿来即用的 Markdown 旅行计划

把旅行规划推进为两份用户可见产物：一份用于集中决策的 `trip-plan-draft.md`，一份只保留执行信息的 `trip-plan-final.md`。默认只让用户参与初始 Brief 和 Draft 决策两个节点。

## 总原则

- 先确定日期、预算、节奏和交通边界，再研究地点。
- 酒店是方案的一部分，不要求用户预先确定。
- 小红书收藏用于判断用户可能喜欢什么；开放时间、价格、票务与交通用官方来源核验。
- Agent 给出“必去候选、推荐、可选、不建议”，最终 must-go 由用户确认。
- 最终稿只写已确认安排，不写落选酒店、淘汰景点或方案争论。
- 每两个地点之间写明交通方式和预计耗时。
- 每天通常不超过两个主要体验；为用餐、休息、天气和晚间轻量散步留出空间。
- 只问会改变城市顺序、住宿区域、预算或每日容量的问题。

## 识别当前阶段

1. 新旅行：从 Brief 开始。
2. 已有初步需求：补齐缺失的关键字段后生成内部 Draft v0。
3. 已有草稿：保留已确认决定，从小红书、酒店或路线研究阶段继续。
4. 酒店、must-go 和固定交通均已确认：跳到动态核验与最终排程。
5. 修改最终稿：只改用户指定范围，并重新运行质检；不得恢复已淘汰内容。

## 0. 初始化项目与语言

- 优先找到已有旅行项目；不要把攻略放进无关目录。
- 新项目使用：`inputs/`、`work/`、`outputs/`。
- 草稿保存为 `outputs/trip-plan-draft.md`，最终版保存为 `outputs/trip-plan-final.md`。
- 中国大陆目的地使用中文。
- 港澳或中国以外目的地使用中文 + 英文正式名称；品牌固有名称不强行翻译。

## 1. 收集 Trip Brief

读取并复用 [assets/trip-brief-template.md](assets/trip-brief-template.md)。最少收集：

- 目的地、日期、出发地、人数与日期弹性。
- 大致游玩意向、节奏、步行和早起接受程度。
- 总预算、每晚酒店预算、房型和取消要求。
- 已知航班、火车、机场最晚到达时间和禁用交通方式。
- 行李、饮食、无障碍、购物等约束。

信息足以决定城市顺序和住宿区域后继续，不为非关键细节阻塞。

## 2. 生成内部 Draft v0

先在 `work/draft-v0.md` 建立：

- 城市顺序和每晚建议住宿区域。
- 每天主题、上午/下午/晚上景点与初步 timeline。
- 城际移动、换酒店、天气敏感日和每日剩余容量。
- 每天主要体验数和预估步行强度。

Draft v0 是研究骨架，不需要先让用户审核，也不要填充虚假的精确分钟。

收到 Brief 后应连续完成 Draft v0、小红书读取和酒店研究，再交付合并后的 Draft v1。除非需要登录/验证码、用户选择收藏夹，或目的地范围存在会改变研究对象的歧义，不要在中间要求用户确认路线骨架。

## 3. 读取小红书收藏夹

需要读取小红书时，必须先加载并遵循可用的 `ego-browser` Skill；优先使用 ego-browser，不使用其他网页抓取或内置浏览器替代。

执行要求：

1. 为本次旅行创建或复用一个独立 task space，并在后续修订中继续复用。
2. 复用用户登录态，只访问与目的地有关的收藏夹。
3. 遇到登录、验证码、收藏夹选择或用户接管时，调用 `handOffTaskSpace`；说明用户要完成的动作。
4. 仅在用户明确说“继续”后使用 `takeOverTaskSpace` 恢复。
5. 读取笔记标题、链接、地点、推荐理由、建议时段、餐次和潜在营销属性。
6. 对重复地点标准化；对高优先级、含糊或冲突的地点打开原笔记继续读取。
7. 完成并确认结果后，用单独的最终 heredoc 调用 `completeTaskSpace(..., { keep: false })`；仅在用户需要查看具体页面时保留。
8. 不把账号信息和无关私人收藏写入文件。

按 [references/research-and-ranking.md](references/research-and-ranking.md) 生成 `work/xhs-collection-analysis.md`，分类为：必去候选、推荐、可选、不建议。分类是 Agent 建议，不是用户最终决定。

## 4. 研究酒店 Options

先根据 Draft v0 确定每段最合适的住宿区域，再找酒店。每段通常给出：

1. 综合首选。
2. 性价比首选。
3. 体验升级选项。
4. 必要时增加预算回落选项。

同一入住日期、人数、房间数、房型、税费、早餐和取消条件下比较。每个 option 必须包含推荐理由和 concern。详细口径见 [references/research-and-ranking.md](references/research-and-ranking.md)。

## 5. 交付 Draft v1

以 [assets/draft-template.md](assets/draft-template.md) 为结构，合并：

- 旅行框架与逐日初步 timeline。
- 小红书景点和餐厅候选矩阵，保留原笔记链接。
- 分段酒店 options。
- 只列真正需要用户决定的路线冲突。
- 可勾选的确认区：酒店、must-go、must-eat、固定交通、机场时间和补充信息。

这是收到 Brief 后的第一次正式方案交付，也是主要决策门。不要在它之前额外发送路线骨架要求确认；也不要在用户确认前进入分钟级最终排程或过度核验所有候选。

## 6. 冻结 Confirmed Decisions

把用户确认内容写入 `work/confirmed-decisions.md`：

- 最终酒店。
- Must-go 景点与 must-eat 餐厅。
- 固定航班、火车和预约。
- 机场最晚到达时间。
- 交通、体力和语言约束。

冻结后不得自行增加大型景点、替换酒店或改变固定交通。新发现只能作为风险提醒，除非用户重新授权调整。

## 7. 核验最终路线

只核验已确认地点：

1. 官方开放时间、临时闭馆、票价和预约规则。
2. 火车、游船、机场交通与日落/闭园时间。
3. 酒店入住、退房、寄存和到车站的真实步行动线。
4. 餐厅营业时间、餐次、预约和排队风险。
5. 地点间步行或公共交通路线及耗时。

日期敏感信息必须重新查询，不复用旧价格、旧班次或搜索摘要。

## 8. 生成最终 Markdown

使用 [assets/final-template.md](assets/final-template.md)。最终稿至少包含：

- 已确认景点 Checklist。
- 固定交通与住宿。
- 超过 1 小时停留复核。
- 每日 timeline。
- 每段地点间交通方式与耗时。
- 餐厅、预约、天气/交通备选和临行复核。
- 支持动态事实的官方链接。

最终稿删除：落选酒店、未采用景点、小红书研究过程、方案比较和“为什么不去”的长解释。

## 9. 运行质检

执行：

```bash
python3 scripts/validate_trip_markdown.py /absolute/path/to/trip-plan-final.md
```

港澳或境外目的地增加 `--bilingual`；禁止打车时增加 `--no-taxi`。修复所有 error，并审阅 warning。随后人工确认：

- 所有 must-go 和 must-eat 均已安排。
- 固定交通与票面一致。
- 换酒店日包含退房、寄存、取行李与入住。
- 机场时间按用户要求反推。
- 文件位于正确旅行项目的 `outputs/`。
