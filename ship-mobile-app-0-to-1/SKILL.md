# 从 0 到 1 交付手机 App

## 总原则

把用户的产品判断转化为可体验结果。不要要求用户先写完整 PRD，也不要在方向性问题上自行猜测。

始终遵守：

- 先确认最终产物、目标设备、真实场景和验收方式，再进入完整开发。
- 只追问会实质改变产品方向、成本或结果的问题；对低风险细节声明合理假设并继续。
- 先打通一条真实核心闭环，再扩展页面和视觉细节。
- 真实使用版本默认空状态，禁止植入示例记录、假指标、假进度或伪造的识别结果。
- 区分设计展示、规则推断和真实能力；不得把启发式标签说成 AI 识别。
- 把已确认页面和决策沉淀为项目约束，后续不得无故推翻。
- 在目标手机尺寸和真实内容下验收，不以桌面浏览器截图代替手机体验。
- 未经用户要求，不擅自扩大到云同步、账号、原生包、通知或上线商店。

## 追问协议

先扫描现有工作区、设计稿、历史决策和运行状态，避免重复询问已有答案。

把不确定项分为两类：

先把用户已经明确表达的条件登记为固定决策，不要把它们改写成“请再确认一次”的问题。只有缺失信息才可以追问。

### 必须追问

仅在答案会改变实现路线时暂停并提问：

1. 最终产物：设计稿、浏览器原型、可安装 PWA、TestFlight/原生 App 或商店版本。
2. 目标设备：iPhone/Android、关键机型、是否必须兼容平板。
3. 真实使用场景与核心闭环：谁在什么情况下完成什么任务。
4. 数据真相：真实数据从哪里来、是否允许本地保存、是否需要账号或跨设备同步。
5. 关键能力边界：哪些必须真实工作，哪些允许暂不实现。
6. 发布和访问：仅本地、共享预览、公开部署或商店分发。
7. 隐私、付费、健康、金融等会显著改变风险的约束。

每轮最多提出 1–3 个彼此相关的问题。提供推荐默认项及其影响，不把整份问卷一次丢给用户。

如果最终形态、设备平台、核心闭环、数据方式和发布入口已经足够明确，先用一句话复述固定决策，然后直接开始，不为形式完整而等待再次确认。用户只说了设备平台但未指定具体机型时，默认覆盖该平台合理的最小和最大屏幕尺寸；只有硬件性能、摄像头或系统版本会改变方案时才追问具体机型。

### 可以假设后继续

对不会改变产品方向的事项，明确写出假设并推进，例如：

- 临时文案、轻微间距和内部变量命名。
- 可替换的技术库或组件实现。
- 尚未指定但易于后续调整的颜色和动效细节。
- 不影响数据和导航结构的微交互。

如果用户未回复非阻塞问题，使用最佳判断继续。不要因“还可以更完美”而停工。

## 阶段 0：建立交付合同

读取 [交付合同模板](references/delivery-contract-template.md)，填写当前已知信息。缺失的方向性信息按追问协议补齐。

至少确认：

- 一句话产品目标。
- 目标用户和真实使用时刻。
- 最终交付形态。
- 首要设备和屏幕尺寸。
- 一条核心任务闭环。
- 真实数据来源与存储方式。
- 必须真实工作的能力。
- 本轮不做什么。
- 用户如何判断“可以体验”。

将确认结果写成简短摘要，请用户确认方向。获得确认后，将其保存到项目现有文档体系；若项目没有约定，使用 `.codex/app-brief.md`。

退出条件：最终产物、核心闭环、目标设备和真实性要求不存在方向性歧义。

## 阶段 1：定义最小可体验闭环

从用户目标反推最少页面和状态，不从功能清单堆页面。

输出：

- 核心流程：入口 → 操作 → 反馈 → 保存/完成 → 回顾。
- 页面地图：只包含闭环必需页面。
- 关键数据对象及来源。
- 空状态、加载状态、错误状态、权限拒绝状态。
- 成功标准和明确不做项。

先实现一条端到端纵向切片。不要先造完整导航或静态页面，再补真实功能。

真实使用版本必须：

- 初始数据为空或来自真实授权来源。
- 所有统计从真实记录计算。
- 示例数据只存在于隔离测试或设计说明中。
- 数据迁移不会把测试记录带入生产。

退出条件：用户能用真实输入完成一次核心任务，并看到真实结果被正确保存或反馈。

## 阶段 2：确认设计基线

将页面标记为：

- `待确认`：允许整体探索。
- `已确认`：实现必须保持结构、信息和视觉意图。
- `局部修改`：只改用户点名区域，其余冻结。

设计确认至少覆盖：

- 首页与核心任务入口。
- 核心操作页。
- 结果/确认页。
- 回顾或详情页（若属于闭环）。
- 空、加载、失败、权限拒绝状态。
- 底部安全区、键盘、刘海/灵动岛和大屏适配。

用户用参考产品描述风格时，提取可执行属性，例如饱和度、圆角、描边、信息密度、动效和语气；不要机械复制品牌。

保存已确认截图、Figma 节点或版本链接。用户手动删掉的信息不得擅自加回。

退出条件：核心页面有可追溯的视觉基线，且清楚哪些区域仍可调整。

## 阶段 3：实现真实纵向切片

按“数据 → 业务逻辑 → 核心交互 → 视觉”的顺序实现，同时保持可运行。

遵循：

- 复用现有项目结构，不在错误的外层仓库修改。
- 先检查工作区是否有用户未提交改动，避免覆盖。
- 将复杂能力拆成稳定边界；例如相机预览、拍摄裁切、主体分割、描边生成和展示共用同一几何坐标。
- 权限、模型下载、网络和存储失败必须有真实反馈。
- 不伪造 AI、云同步、通知、识别准确率或原生能力。
- 对首次加载较慢的模型提供清晰状态和失败原因。
- 保持生产数据与测试 fixture 隔离。

每完成一个可验证子闭环就运行相关检查，并给用户简短进展。持续工作时不要长时间静默。

退出条件：目标手机上的核心路径可完整操作，数据和能力陈述真实。

## 阶段 4：移动端验收与防回归

读取 [移动端验收清单](references/mobile-acceptance-checklists.md)，只加载适用于当前形态的部分。

至少验证：

- 最小和最大目标屏幕宽度。
- 顶部与底部安全区。
- 触控热区、滚动、横向溢出和键盘遮挡。
- 真实空状态和真实数据。
- 刷新、重新打开和失败恢复。
- 关键权限允许、拒绝和重新授权。
- 生产构建而非只测开发模式。

涉及相机、相册、抠图或音视频时，建立真实输入回归集。每次算法调整都运行整组，不能只验证刚修复的一个样本。

对视觉算法同时检查成功率、主体完整性、背景残留、几何对齐和边缘质量。优先保证用户任务完成，不为追求“干净”而把真实输入全部拒绝。

退出条件：核心闭环、目标设备矩阵和历史高风险问题全部通过；已知限制被明确记录。

## 阶段 5：预览、Git 与发布

先交付可访问预览，再请求用户体验确认。

预览要求：

- Web/PWA 通过本地 HTTP 或 HTTPS 服务打开，不让用户直接双击 `index.html`。
- 明确提供唯一的当前体验地址。
- 说明本轮改了什么、没改什么、如何验证。
- 若存在缓存，提供版本号并验证用户看到的是最新构建。

默认 Git 节奏：

1. 从最新主分支创建独立功能分支。
2. 完成修改和验证。
3. 给用户预览确认。
4. 创建 commit 并 push 功能分支。
5. 合并到主分支并 push。
6. 从主分支的确切 commit 构建和部署。
7. 在生产地址重新验证页面、控制台、资源和版本。

除非用户明确要求直接发布，否则在用户确认前不要合并或部署。部署成功状态不等于体验成功，必须打开生产版本复验。

退出条件：生产或目标分发渠道指向已验证的确切版本，且用户拿到唯一体验入口。

## 阶段 6：交接与后续

交付时说明：

- 当前体验地址和版本。
- 已完成能力。
- 未完成或有条件限制的能力。
- 数据保存位置和丢失风险。
- 验证结果。
- 下一步建议及其优先级。

长项目或准备换对话时，生成 handoff，记录已确认设计、不可违反约束、关键代码、测试方式、历史故障和部署流程。引用现有文档和 commit，不重复粘贴大段内容。

## 沟通格式

每轮开始用一句话说明本轮范围和不会改动的部分。

中途更新只包含：

- 已确认的判断。
- 已完成的可验证结果。
- 当前风险或非阻塞假设。
- 下一步。

每次交付统一给出：

1. **结果**：现在可以做什么。
2. **本轮变化**：只列用户可感知内容。
3. **验证**：在哪些设备/路径下通过。
4. **体验入口**：一个明确地址或安装方式。
5. **已知限制**：不得隐藏。

不要用工具日志代替结果，不让用户从多个地址或多个版本中猜哪个最新。

## 失败保护

遇到以下情况立即停止当前路线并回到对应阶段：

- 用户说“这不是我要的产物” → 回到阶段 0。
- 用户说“不要再改这个页面” → 将页面标为已确认并回到阶段 2。
- 真实数据被示例数据污染 → 回到阶段 1，清理生产初始化和迁移。
- 同类视觉/媒体 bug 再次出现 → 回到阶段 4，补回归样本和自动检查。
- 本地可用但部署白屏/旧版 → 回到阶段 5，检查构建包、资源路径和缓存。
- 用户连续两次指出同一问题 → 不继续局部打补丁；先确认根因、添加防复发验证，再修改。
